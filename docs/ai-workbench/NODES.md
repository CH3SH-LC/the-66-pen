# 节点方案

分母来自 `data/node-workbench/catalog.json` 的实测/解码集合，不从工具支持列表倒推。
`node-coverage.json` 对每个变体列：definitionId、graphKind、配方是否存在、唯一合同数、
未知字段数、运行验证。查询 `knowledge.node` 同时返回原始节点、配方、合同和下一步。

节点身份包含完整 category variant；至少指定 `definition_id` 与 `graph_kind`。
20000 是服务端图；20001、20002、20007 是不同客户端图，不能只按名称互换。
唯一匹配失败时返回候选，禁止选第一个。端口 shell kind、index 和泛型类型都要匹配。

每份已有配方包含：

1. 创建/查找图的 argv 模板，以及新节点 `buildPlanNode`。
2. 输入输出端口签名、连线规则和参数候选存储槽。
3. 动态端口、泛型选择、菜单可见性和顺序要求。
4. 当前实例 slots 的读取要求及运行证据边界。

`graph.compile` 用结构化 nodes/edges/values 创建不可变计划：
最多 128 节点、1024 边、256 值，还受原生请求字节上限限制。
值用明确标签 `{ "float": 1.5 }`、`{ "bool": true }`、`{ "vector3": [1,2,3] }` 等。
先 `describe graph.compile` 看完整类型。节点索引是本计划内索引，不能当已保存 nodeId。

执行前用当前桥会话创建/查找图，并读取真实 slots。`unknown`、未录制端口、
动态槽位置、泛型待解析都不是可以猜的默认值。输入若只到编译阶段，必须继续按
真实 author 工具创建/写入/绑定，原生保存后独立读回；运行效果仍需试玩。

玩法常见差异：

- 实体 ID、玩家角色实体、玩家 ID、道具 ID、模板 ID 必须按端口类型转换。
- 商店新商品和改已有价格是不同节点；既有方案中的 707/710 不可互换使用。
- 保存里能读到文字不证明游戏 UI 展示或账号有对应文本权限。
- 旧 activities/demo 是固定场景验收记录，通用构建用 gameplan + 当前图/实体工具。

本库完整列出已录制变体的未知项；“都有配方”不意味着官方所有功能已完成真机验证。
