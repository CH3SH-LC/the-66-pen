# 构造字典的节点 — 两个 id 命名空间同步检索 (DICT-CONSTRUCT-SEARCH)

日期: 2026-10-10
范围: 纯离线只读。未连 bridge、未发节点图请求、未起/未碰游戏与编辑器、未写任何存档或 `.gil`。
任务: 在**两个 id 命名空间**里同时找"构造字典"的节点 ——
(a) 桥的 uint32 `definitionId`（`data/node-contracts/**`），
(b) 离线目录的 64-bit `resourceNetworkId`（`docs/editor-catalog/NODE-CATALOG.md` / `node-catalog-full.json`）。
检索键: 输出 `serverParamType`/`type_kind` ∈ {27, 10003}，**以及**节点名含
`字典 / 拼装 / 组装 / 构造 / 创建 / 建 / 添加 / 合并 / map / dict`。

> 姊妹文 `DICT-WRITE-PROBE.md` 已从"可写性"角度给出 (A)/(B) 判决。本文的**增量为命名空间维度**：
> 64-bit 目录里**有没有** uint32 store 里没有的构造器。回答见 §4。

---

## 0. 结论先行 (verdict)

**两个命名空间的结果完全对称 —— 它们不是两个节点集，是同一节点集的两套 id。**

| 检索方式 | uint32 命名空间 | 64-bit 命名空间 |
|---|---|---|
| **按类型过滤**（输出类型 = 字典 27 / 10003） | 18 条 pin，其中 8 条输出，**0 个构造器** | 18 条 pin，其中 8 条输出，**0 个构造器**（同一批） |
| **按名字过滤**（含"字典"） | **29 个节点**，其中构造器 **4 个**（1088/1788 + client 200152/200153/200228/200229） | 同样这 29 个节点，构造器相同 |
| 该命名空间**独有**的构造器 | — | **0 个** |

**关键回答（对任务书里那个条件句）**：
> 「64-bit 命名空间里有、uint32 里没有的候选」——**不存在**。

两个命名空间**都有**构造字典的节点（`建立字典`、`拼装字典`），而且是**同一批节点**：
64-bit 目录的 799 个 id **是** uint32 store 810 条 `resourceNetworkId` 的**真子集**（§4 已验：目录 − store = 0）。
所以本题的正确答案既不是"只在 64-bit"，也不是"哪都没有"，而是：
**两边都有，且两边逐条对应 —— 差集为空。** 唯一"一边有另一边没有"的 11 个节点是 7.1 新增
（`实体是否携带指定单位状态`、`战术：空中*` 等），**与字典无关**。

**真正值得上报的一条**：`CLAUDE.md:74` 的
「写字典常量（contract 类型 27）——500 条定义里没有一条构造字典」**是过度概括**。
在**它自己限定的 type-27 过滤器下成立**（type-27 输出里确实没有构造器），
但作为"没有构造字典的节点"这一泛命题**是错的**：
`建立字典`(1088)、`拼装字典`(1788) 就在那 500 条 server 定义里，
只是因为它们的输出声明为 **Generics (10000)** 而非 27，被类型过滤器**结构性地漏掉**。
（这正是 memory「搜不到 ≠ 不存在」的同型陷阱：断言没错，由它推出的结论越界了。）

---

## 1. 名词对齐：为什么"类型过滤"必然漏掉构造器

先把两个"字典类型码"钉住（它们在契约的不同字段上，值不同但指同一件事）：

| 字段 | 位置 | 字典的取值 | 出处 |
|---|---|---|---|
| `valueTypeValueRaw` / 目录 `type_kind` | 引脚"值的类型" | **10003**（脚本内 `valueTypeNameRaw="10003"`） | `data/node-contracts/shared/value-type-codes.json`（`10003`→字典，18 条 pin）；`docs/editor-catalog/NODE-CATALOG.md:1553` |
| `serverParamType` | 引脚"物化后的槽位" | **27** | 仅在 live-read（uint32 store）里出现，见 §2 |

两者的对应关系：`serverParamType == 27` 的 18 条 pin **全部** `valueTypeValueRaw == 10003`
（本文 §2 实测，28/28 无例外；`10003` 本身**从不**出现在 `serverParamType` 字段）。
即 **27 = "已被物化成具体字典的槽位"，10003 = "值的类型是字典"。**

**为什么构造器躲开了这两个码**：`serverParamType` 的分布里 **`10000`(Generics) 从不出现**
（泛型 pin 的 `serverParamType == 0`，只有 `valueTypeValueRaw == 10000`）。
`建立字典` / `拼装字典` 的字典输出声明为 **Generic(10000)** —— 由编辑器在被连到具体槽位时反推类型。
因此**任何只按 27 / 10003 过滤输出 pin 的搜索，天生看不见构造器**。这是结构性盲区，不是数据缺失。

## 2. 检索一：按输出类型过滤（27 / 10003）—— 两命名空间一致，0 构造器

### 2.1 uint32 命名空间（`data/node-contracts/variants/**`）

对 `ports[].serverParamType == 27` 全量过滤（不分方向）：

- 命中 **18 条 pin**，方向拆分 **input 10 / output 8**；
- **8 条输出**（`valueTypeValueRaw` 一律 10003）**全部是"向运行时状态/事件要一个字典"的读/事件节点**，
  无一条从输入构造：717 / 718 / 719 / 721 / 722 / 730 / 731（查询/获取）+ 705（事件回执）。

### 2.2 64-bit 命名空间（`.runtime/editor-catalog/node-catalog-full.json`）

同一过滤器，改用目录字段 `pins[].type_kind`（`class 4` = 输出数据）：

- 命中 **18 条 pin**，方向拆分 **input(class 3) 10 / output(class 4) 8**；
- 8 条输出与 §2.1 **逐条同名同量**（仅 id 换成 64-bit 哈希），仍是查询/获取/事件，**0 构造器**。
- `type_kind == 27` 在整个 799 目录里**从不出现**（直方图 §4）。

**小结**：无论在哪套 id 里，按 27 / 10003 过滤输出，都拿不到构造器。这一步**不构成**"没有构造器"的证据。

## 6. 对既有文档的更正建议（本文档不改任何代码/他文）

1. `CLAUDE.md:74`「写字典常量（contract 类型 27）——500 条定义里没有一条构造字典，只有 7 条读字典」：
   - 前半句应限定为「**type-27 输出里**没有构造器」；作为泛命题**被证伪**（1088/1788 存在）。
   - 「只有 7 条读字典」按本文口径是 **8 条 type-27 输出**（7 条查询/获取 + 1 条事件 `705`），
     数字需复核（`DICT-WRITE-PROBE.md` 亦记了同一处 705 的出入）。
   - 建议改为：「无 **type-27 输出的**构造器；字典构造器存在（**1088 建立字典 / 1788 拼装字典**，
     server + client 镜像 200152/200153/200228/200229，输出均为 **Generic(10000)**），
     但 generic→concrete(27) 的物化**未上机**。」
2. `data/node-contracts/shared/value-type-codes.json` 的 `note` 说
   "no contract field is filled from it（HistoricalInferredNames）" —— 无碍；
   但可补一句：`serverParamType=27` 与 `valueTypeValueRaw=10003` **是同一字典类型的两个字段视图**，
   前者只出现在 live-read，后者是资源解码口径。
3. `docs/editor-catalog/NODE-CATALOG.md:1762`（节点字段 107 = "变长参数"标记，
   27 个节点含「拼装列表/拼装字典/拼装结构体」）：`拼装字典` 的 101 个引脚正由此而来 ——
