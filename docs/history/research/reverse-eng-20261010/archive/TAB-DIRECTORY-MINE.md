## 2. 问答二：`未分类页签` 是引擎会造的名字，还是赝品？

**名字本身是引擎词表里的**，不是赝品：

- `docs/editor-catalog/UI-TEXT-INVENTORY.md:189` 记 UI 键名 `..._DEFAULT_UNCLASSIFIED_TAB` → 文本 **`未分类页签`**；
  `.runtime/editor-catalog/string-table.json` 里该常量名实际存在（`DEFAULT_UNCLASSIFIED_TAB`）。
- 用户**自己的原件**里，40 条中就有 **30 条**叫 `未分类页签`（见 §1.1），这是编辑器给「未归类资源」的默认名。
- 所以这个名字**是引擎的词**，把它当「被打进去的乱码」是错的。

**这一点能推出什么、不能推出什么**：

- 能推：`name=未分类页签` 不能当作「该条是损坏」的证据——引擎自己就产这个名字。
- 不能推：名字合法 ≠ 条目合法。**待解释的是「这条没有 field 1」**，名字只是它挂在引擎默认名上。

## 5. 结论与对当前风险的影响（一句话版）

1. **「谁在追加」的答案**：是**存档写入方**（游戏/编辑器进程），不是本工程的 Python（P1）。
2. **它不是「每次 save 各加一条」的失控增长**（P3），也不是随机的字节损坏——追加是**纯粹的、
   逐字节可复现的尾部拼接**（P2），且**无 id 那条在所有 121 处字节完全相同**（§1.3）。
   所以把整件事叫「字节损坏」不准确；更贴近证据的说法是
   **「写入方把内存里的页签目录里、关卡文件缺的两条，补齐到尾部」**，其中一条没有 field 1（U2：可能只是 id==0）。
3. **最关键的风险成立**：**文件级恢复不能治本**（P6）。只要写入方内存里那份目录仍是 42 条，
   恢复成 40 后**下一次 save 就会重新追加**——10-10 00:41 已重演一次。
4. **但「每次 save 都会复发」为假**（P3）：不改变目录状态的 save **不动** field 6/46。所以「复发」的触发是
   **save 本身 × 写入方目录仍多两条**，而非「save 本身」。
5. **给 `level_directory.py` 的一条提示**：`missing-entry-id` 这个 defect 名**可能是假阳性**——
   若 U2 的「id=0」读法成立，这条是**合法但隐形**的页签。**在能区分二者之前，别把它当必删的损伤。**
   （工具本身只读、只在磁盘上判「field 1 在不在」，这一点没错；错的是**对它的解释**。）
