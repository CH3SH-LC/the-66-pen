## 0. 一句话结论（先摆）

1. **写这份存档的不是本工程的 Python，是游戏进程（`YuanShen.exe`）。** 我们的 `save` 只是让游戏
   **调用它自己的存档函数**（`SaveCurrentLevel(save_manager)`）；字节由引擎序化并落盘。
2. **追加发生在 save 事件，但不是「每次 save 都追加」**——只有写入方内存里的页签目录比磁盘文件多时，
   save 才把多出来的条目**纯尾部补写**上去。
3. **同一条尾巴（无 `field 1` 的 `未分类页签`）在本关卡之外也出现**——关卡 `1073741830`、`1073741840`、
   `1073741841` 都带**逐字节相同**的那条，且 `1830` 的那条 mtime 早到 **2026-09-19**，**早于 10-08 事件**。
   ⇒ 这是**写入方的行为**，不是我们一次 save 造出的孤立字节损坏。
4. **判决：倾向 (b) 引擎/写入方行为**（由 (a)「我们的 save 触发」点火）。**因此它会复发**——文件级恢复
   治不了本，只要写入方内存里那份目录仍多两条，下一次 save 就原样再补回来（10-10 00:41 已重演）。

## 2. 问答二：`keep_registered.py` 与 10-08 事件的归档证据，事件的结论是什么

### 2.1 `tools/beyond-save/keep_registered.py` 说了什么（写入方不重读文件）

模块 docstring（`keep_registered.py:5-9`）原文：

> “register_level.py writes a new archive into the player profile, and **something else
> -- the game or the editor -- rewrites that profile from its own memory**. A single
> write is therefore always lost: at 13:32 the file on disk held our 380-byte version and
> the writer replaced it with its own 323-byte one, **which proves the writer does not
> re-read the file before writing**.”

这条是**归属的总钥匙**：写入方**从内存序化**，**不回头读盘**。所以「文件里是什么」不影响「它写出什么」——
把盘上文件恢复成 40 条，不能改变它内存里的目录。

（补充同类证据：`tools/beyond-save/attribute-save-writes.py` 就是为回答「哪个进程在写」而写的；
其留档 `.runtime/beyond-save/write-attribution.log:1,8-10` 在本机实测把一次 `.gip` 改写**归给了
`pid 113168 (YuanShen)`**，不是任何一个 `BeyondEditor` 进程。）

### 2.2 10-08 事件自己的结论（`PROGRESS-BY-FUNCTION.md:118-125`）

原文（§四.2，`docs/PROGRESS-BY-FUNCTION.md:118-120`）：

> “**2026-10-08：关卡文件 `1073741842.gil` 的目录段被弄坏。**
>   - `root field 6` 从用户原件的 **40 项**变成 **42 项**，其中第 41 项**缺 `field 1`**（一个没有 id 的页签条目）。
>   - **成因：当轮为了清掉自己留下的测试实体，做了两次 save；两次 save 各追加了一项，其中一项残缺。**”

同一节还留下未决问题（`PROGRESS-BY-FUNCTION.md:125`）：

> “**仍未查明**：引擎下一次保存会不会**再次追加** field 6/46 的项 ⇒ 本次恢复会不会被后续保存覆盖。
>   若在编辑器内保存过，须重新核对。”

归档侧的对应结论（`.runtime/_ledger_close.py:29-31`，写入 round-ledger 的收尾条目）：

> `"measuredDamageRange"`: “… field 6 前 40 项与原件逐字节相同，追加的 2 项中第 42 项缺 field 1。”
> `"whatRemainsUnknown"`: “… **引擎下一次保存是否会再次追加 field 6/46 的项未查明** ⇒ 本次恢复会不会被后续保存覆盖未知。”

**所以 10-08 事件当时把成因归给「我们那两次 save」**（(a) 读法），并把「引擎会不会再追加」**明列为未查明**。

### 2.3 本次实测对 10-08 结论的两处修正（有字节支撑）

1. **不是「两次 save 各追加一项」，是「一次 save 追加了两条」。** scene-cli 的 before/after 成对留档里，
   关卡 1842 出现追加（root6 `40→42` **且** root46 `1→2`）**只有两次 run**，每次**一步到位加两条**：
   - `.runtime/game-executor/scene-cli/20261008-211737-save-309a4b70`：`before-1073741842.gil` root6=**40** → `after-…`=**42**（field46 `1→2`）
   - `.runtime/game-executor/scene-cli/20261010-004106-save-640895e1`：`40 → 42`（field46 `1→2`）

   其间的 `20261008-211541-save-1c99e513` 是 `40 → 40`（**同一晚、同会话、不追加**）。
   ⇒ 追加**不是**「每次 save 一条」的失控增长；是**一次 save、两条**、且**有条件的**（§4）。
   （同一结论见 `TAB-DIRECTORY-MINE.md` §4.1 (P5)。）
2. **「成因是我们那两次 save」这句要收窄**：触发的确是 save（我们发的），但**写入的字节不是我们造的**
   ——本工程**没有任何一处 Python 会写关卡的 `field 6`/`field 46`**（§4.1 (P1)）。save 只是**让引擎把
   它内存里的目录序化出来**。因此「成因」应读作「**触发**」，不是「**作者**」。

## 4. 问答四：判决——(a) 我们的 save、(b) 引擎行为、还是 (c) 未知

### 4.1 已证（可复核）

**(P1) 树里没有任何 Python 写关卡的 `root field 6`/`field 46`。**
Bash `grep -rn "Field(6" tools/ --include=*.py` 的全部命中只有**两个测试**文件
（`tools/gameplan/tests/test_levels.py:78`、`test_level_report.py:83`）。生产侧 `build_level`
（`gil_container.py:289-292`）注释明写「replacing only the name -- **and field 1 only if it was there**.
A file that never carried field 1 must not gain one」。`ROOT_FIELD_DIRECTORY`（`level_directory.py:66`）
只被只读的 `level_directory.py` 用；`build_tab`/`_rebuild_tabs_holder`（`gil_container.py:419,479`）
作用于 **`.gip` 的 profile**，不是关卡 `.gil`。
⇒ **能写这两个字段的只有「存档写入方」（游戏/编辑器进程）。**

**(P2) 写入由游戏进程执行。** save 走的是原生同名调用：
`tools/game-executor/native/game_scene_action.cpp:214-216`（`HR_ACTION == 2`）把游戏自己的
`SaveCurrentLevel` 函数指针（`moduleBase + HR_SAVE_ANCHOR_RVA`，RVA 见 `:38`）与它自己的
`save_manager` 交给 `ge::scene::save_current`；后者（`tools/game-executor/native/scene_calls.cpp:52-55`）
就是 `save(save_manager)`——**在游戏进程里调游戏自己的存档例程**。同文件 `:223-226` 的注释把这一点钉死：
「**This is a receipt, not evidence of persistence.**」（回执只说调用返回，不等于落盘）。

### 4.2 未证（不编）

- **(U1) 写入方内存里为什么是 42 条——没坐实。** 已确证**不在** `.gip`（那里只有 9 条另一张表，
  `gil_container.py:390-391 parse_tabs`）。最贴合证据的读法：save 把**运行中的编辑器/游戏当前资源树**
  序化进关卡，内存里已有 42 条而文件是旧快照，于是**补齐差的两条**。**为何内存是 42，没坐实。**
- **(U2) 无 id 那条是「`id=0` 被 proto3 省掉」还是「id 从未赋值」——磁盘上不可区分（同一串字节）。**
  本工程已有 proto3 省零值的判例（`entity_geometry.py:54`）。若该页签 `id==0`，`field 1` 必然永不出现，
  可自洽解释「唯一一条无 id」。**本文不选边**；但正因如此，`missing-entry-id` 这个 defect 名
  **可能是假阳性**（见 `TAB-DIRECTORY-MINE.md` §5.5）。
- **(U3) 跨会话是否复发——未知。** 同一写入方目录状态下**会**（P5 实测）；重启编辑器后内存是否会
  重同步回 40，**无证据**。

### 4.3 判决

> **属于 (b) 引擎/写入方行为，由 (a)「我们发出的 save」触发，而非 (c) 未知。**
>
> - **作者**是游戏进程（引擎序化内存 → 尾部拼接），不是我们的代码（P1、P2）；
> - **时机**是一次 save，**当且仅当**写入方内存里的页签目录比盘上文件多（P4）；
> - 它**跨关卡、跨三周、字节相同**地出现（§3），所以**不是** 10-08 那一次 save 的孤例；
> - 10-08 事件把成因写成「我们的两次 save」——那是**触发**层面的对，**作者**层面应改为写入方
>   （§2.3 的两处修正）。

**复发判据**：**会复发**（P5）。只要写入方内存里那份目录仍是「多两条」的状态，**下一次 save 就再补一次**
——文件级恢复（10-08 那次做的）**不是解**。要止血，只能从**写入方那一侧**动手（让编辑器内存重同步到
40，或不再发 save），这三条路**都超出本文（只读）的边界**，本文不提修复授权。
