## 0. 一句话判决

> **技能资产和货币/道具/商店/背包模板是「同一类东西」（同一 KIND：带类型化配置ID、经编辑器 UI 【新建…】按钮创建的编辑器资产），
> 不是另一套子系统。因此「建编辑器资产模板」这**一条缺失原语**同时是
> game A 技能创建与六模块场景半边（模板部分）的共同堵点；打通它，两处一并解锁。**
>
> 但判决必须带两条**不同轴**的 caveat（否则是过度承诺）：
> ① 六模块场景半边里**另一半是「给实体加组件」**（M1 碰撞触发器 / M5 商店组件），属**另一条**原语（`PRIMITIVE-VERDICTS.md:64` #5 = **无**），**不会被建模板解开**；
> ② 技能比货币/道具**多三层写面**（动画 / 事件轨道 / 槽位绑定），同在**同一块技能面板**内、**同乘一条路**（`SKILL-ASSET-MINE.md` §4.3）。

判决用语三态（`SESSION-LESSONS.md` §一）：本判决的核心命题是 **CONFIRMED（有正面逐字证据）**；
「技能也序列化在 `.gil root field 15`」仍是 **not_found→undecidable**（本机无 type-6 实例，见 §6）。

## 1. 问 1：技能资产 = 货币/道具模板**同一类**，还是**另一套子系统**？

**判决：同一类（同一 KIND）。** 判据是「是否是『带类型化配置ID、由编辑器 UI 新建出来的编辑器资产』」——
拆成**四条独立判据**逐一逐字对照，四条全中：

| 判据 | 货币 / 道具（资源系统族） | 技能（战斗预设族） | 逐字出处 |
|---|---|---|---|
| **① 是「模板/资产」而非运行期实体** | 道具：「点击**新建道具**按钮，在弹窗内选择确认创建即可新建一个**道具模板**」 | 技能：「技能是一种通过接收游玩时的用户输入，让角色执行某一段预设行为的**封装**」；创建产出「一份技能」 | `mhbgx0rspbqu.json:32`；`mho81frl33im.json:19,35` |
| **② 唯一标识 = 配置ID** | 货币：「配置ID：**货币数据的唯一标识**」；道具：「配置ID：**道具模板的唯一标识**，可在节点图中使用」；商店：「配置ID：**商店模板的唯一标识**，被商店组件进行引用」 | 技能：「配置ID：**技能的唯一标识**，在节点图修改对应的技能配置时，引用该ID」 | `mh2cr30yeak0.json:44`；`mhbgx0rspbqu.json:38`；`mhi9s7isvp50.json:74`；`mho81frl33im.json:41`；`mhj4a0rzu4pi.json:56`；`mhftoirpwd46.json:44` |
| **③ 同一套「UI 新建 + 弹窗确认」手势** | 道具：入口＝**道具页签→新建道具→确认创建**；商店：**「点击‘新建商店模板’即可添加并编辑模板」** | 技能：三章同句——「技能编辑的入口位于**战斗预设页签的技能页签下**…【新建技能】…【确认创建】」 | `mhbgx0rspbqu.json:32`；`mhi9s7isvp50.json:62`；`mho81frl33im.json:35`；`mhftoirpwd46.json:38`；`mhj4a0rzu4pi.json:50` |
| **④ 同一张「配置ID」类型表** | 类型 `8=普通道具、装备道具`、`10=资源货币`、`11=道具背包`、`15=商店模板` | 类型 `6=自定义技能`、`28=造物技能`、`37=角色操纵技能`（＋周边 `31=技能属性组`、`32=技能变量`） | **同一张表**：`mhsd6lrx3voe.json:64`（逐字见 §4） |

**第四条是全判决的锚**：官方《ID修改》章的小节「五、数据规则 / 2.ID类型表」把货币(10) 与技能(6/28/37)
**排进同一张「配置ID / 对应类型 / 十进制ID可修改的范围」三列表**（`mhsd6lrx3voe.json:64`，
evidence 同表 `:66`）。**同一张类型表 = 同一套 ID 分配合规 = 同一个数据模型家族**，这不是比喻。

### 1.1 边界（必须点破，否则「同一类」会被读成「同一个面板」）

- **UI 归属不同模块，但同属「编辑器资产」这一类**：`mhexhcr1qjh2.json:18` 的「战斗预设」五模块＝
  「**玩家与职业编辑 / 单位状态编辑 / 技能编辑 / 本地投射物编辑 / 道具编辑**」——**技能与道具在同一块 UI 模块（战斗预设）里**；
  **货币/背包/商店另走**系统菜单【货币与背包】/【商店模板管理】（`mh2cr30yeak0.json:26`；`mhi9s7isvp50.json:62`）。
  ⇒ 技能与**道具**同 UI 模块；技能与**货币**分属不同 UI 模块，**但共用同一张配置ID 类型表**。
- **doc 分类不同**：技能挂 `概念介绍 / 高级概念` 直下；货币/道具/商店挂 `高级概念 / 资源系统`。
  这是**概念分类树**，不是数据模型——数据模型上它们同表同段（§1 表第 ④ 行）。
- **技能是「复合资产」，货币/道具是「叶子模板」**：技能内含技能动画（独立资产）、事件/状态轨道，
  并可挂技能节点图（`SKILL-ASSET-MINE.md` §1 表行 9/11；`mho81frl33im.json:29-31`）。
  **⇒ 同类不同复杂度**（不影响「同类」，但影响 §2 的 caveat ②）。
- **可导出 .gia 也同族**：`mhxbd59urbfu.json:32` 逐字「**战斗预设 - 技能，状态，道具**」——
  技能与道具同列一张可导出清单。

**⇒ 问 1 答案：同一类。** 差别只在「UI 挂在哪个模块」与「内部结构复杂度」，**不在数据模型家族**。

## 2. 问 2：同一条原语是否一并解开「六模块场景半边」与「game A」？

**先说清两边各自卡在哪（都用被挡清单的 file:line 说话）**：

- **game A**：`docs/NEW-FEATURE-PLAN.md:126` 逐字——
  「**3 个可学习技能** | ✗ **技能是编辑器资产，节点图只能按配置 ID 引用**——必须先在编辑器里建出来，这是硬前置」；
  `:151` 明写游戏 A 额外要「**必须先由编辑器建出来的技能资产**」。
- **六模块场景半边**（`docs/gameplan/DEMO-GAP.md:74-80` 的「❌被挡的那一半」列）拆成两类：
  - **模板类**：M2 类型10 货币模板（`:75`）、M3 类型8 道具模板（`:76`）、M4 类型11 背包模板（`:77`）、M5 类型15 商店模板（`:78`）——**全是「建编辑器资产模板」**；
  - **组件类**：M1 碰撞触发器组件（`:74`）、M5 商店组件（`:78`）——**是「给实体加组件」**。

**判决：**

1. **「建编辑器资产模板」这一条原语，同时是 game A 技能 与 六模块的 M2/M3/M4/M5 模板 的共同堵点。**
   证据：两边的「必须人工建」步在 `DEMO-GAP.md:94`（第 1 步：手工建货币/道具/商店模板）
   与 `NEW-FEATURE-PLAN.md:126`（技能是编辑器资产）中**被描述为同一个能力**；
   而命令面复核显示**没有任何一条建模板/建技能的写入口**——
   桥 op 现场现值（见 tools/gameplan/tests/test_doctrine.py）（`grep -c 'case "' tools/editor-bridge/ManagedBridge/BridgeServer.cs`，本次 checkout 实测；
   该值由 `tools/gameplan/tests/test_doctrine.py` 的 `BridgeOpCount` 双向钉住，**不照抄手写数**），
   其中 `grep -in "skill|技能"` **0 命中**；原生动作集仍是 **6** 项
   （`NATIVE_ACTIONS = ("inspect","create","save","create-batch","reopen-current","creature-create")`，
   `tools/editor-bridge/elevated-request.py:339`）——**无一项建资产/建技能**。
   节点图侧**只能按配置ID 引用技能**：端口名「技能配置ID」在 `data/node-contracts/variants/server/bucket-00.json:4652`，
   另有节点「根据技能实例ID获取技能配置ID」（`data/node-contracts/definitions/bucket-01.json:10594`）——
   **能读、能引用，不能造**。
   ⇒ 两处卡的是**同一堵墙**：`TEMPLATE-CREATION-MINE.md:207-218` 把它命名为
   **「谁在 `.gil root field 15` 追加一条带类型化配置ID 的记录」**（落点候选见 `:104-151`）。

2. **但要写清「不是全部」**——两处各还有**别轴**的缺口，**建模板不负责**：
   - **六模块的组件半边**（M1 碰撞触发器、M5 商店组件）要的是**「给实体加组件」**，它是 `PRIMITIVE-VERDICTS.md:64`
     判为 **无** 的**另一条**原语（`AddComponent/CreateComponent/AttachComponent/InsertComponent`
     在四处检索范围全 0 命中；`CLAUDE.md:104-119` §六(a)）。**建模板不会解开它。**
   - **技能的三层附加写面**：技能动画引用 / 事件轨道 / 槽位绑定（`SKILL-ASSET-MINE.md` §4.3、
     `mho81frl33im.json:29-31`）。它们**都在同一块技能面板内**，所以**同乘一条路**（一旦进得了那块面板就能一起落），
     但仍是**额外要落地的字段**；且技能动画本身是**独立资产**（`mh57xz9afh7e.json`）。

**⇒ 问 2 答案（plainly）**：**是的——「建编辑器资产模板」这一条原语，会一并解开 game A 技能创建
与六模块场景半边的模板部分（M2/M3/M4/M5）。** 但它**不**解开六模块的**组件**半边（M1/M5 组件），
那是 `PRIMITIVE-VERDICTS.md:64` 的另一条原语；也不把技能的动画/轨道/槽位三层**白送**，只是让它们落到同一条已通的路里。

## 3. 问 3：（「若是另一套子系统」分支）—— **不成立，但记下它不是子系统的原因**

问 3 写的分支是「如果是不同子系统，命名它并说需要什么」。**本判决不落入该分支**：技能不是
独立子系统，而是「编辑器资产 + 配置ID」这一 KIND 的**另一实例**。若将来要反驳本判决，
最可能的反证形状是「技能**没有**配置ID、或**不走**那张类型表」——而两条都被 §1 第 ②/④ 行的**逐字官方原文**否掉
（`mhsd6lrx3voe.json:64` 的 `6=自定义技能/28=造物技能/37=角色操纵技能`）。

**因此这里不命名新子系统，只重申**：技能需要的东西 = 模板需要的东西（建带配置ID 的资产记录）
+ 组件不涉及的三层附加写面（§2 caveat ②）。

## 5. 问 5：既得此答，**下一件最该挖的事**

**判决给出的一件事**：技能与模板共用**同一堵墙**，这堵墙在**同一块从未被逆向的前端面板**里。

**⇒ 最该挖的一件事：逆向主编辑器的「战斗预设 / 系统菜单」外壳（加密的 `assets.bin`），
取回【新建技能】与【新建道具/货币/商店模板】这些按钮**派发的命令名（命令 → 前端服务 → 后端落点）**。**

为什么是这一件（三条理由，全部可引）：

1. **它是两边唯一的公共未逆向面**：`UI-TEXT-INVENTORY.md:515` 记「全库检索 `战斗预设` = **0 命中**」；
   `:574` 自述主外壳中文界面文本「很可能封装在 **`assets.bin`**（ZIP，内含 1 个加密成员…）…**本工程尚未解包**」；
   `TEMPLATE-CREATION-MINE.md:70-74` 亦指出系统菜单面板 0 命中。**一次挖，同时服务 game A 技能与六模块模板**——单投双收。
2. **它是「命令名」的唯一来源**：`command_route` 38 行里没有任何一条建模板/建技能
   （`TEMPLATE-CREATION-MINE.md:41-59`），**因为那块 UI 不在已逆向语料里**；要找到「新建」按钮真正派发的命令名，
   只能回那块面板取。拿到命令名，才谈得上在 `commands` 哈希扫描里查原生落点（同上 §4.3）。
3. **它把落点候选钉成靶**：拿到命令名后，配一次**非黑即白的判别实验**把磁盘落点坐实——
   **人在编辑器里建 1 个技能**（战斗预设→技能页签→新建技能→确认创建）→ 原生 `save` →
   离线重扫该关卡 `.gil` 的 `root field 15`：若新增一条 `id ∈ 6=自定义技能` 区间
   （`1098907648~1103101951`，`mhsd6lrx3voe.json:64`）⇒ **技能也序列化在 field 15**，
   目标随即具体化为「**谁在 field 15 追加一条记录**」（`SKILL-ASSET-MINE.md` §6 的判别实验，与
   `TEMPLATE-CREATION-MINE.md:220-232` 同形；**一次 UI 点击 + 一次 save**）。

**先后次序**：**先跑判别实验（约一次点击 + 一次 save，成本近零、非黑即白）把落点坐实，
再投入 `assets.bin` 的面板逆向**（231 MB、encrypted flag=1，是重活）——先用最便宜的一步砍掉一半不确定性。
**不要**在没有落点结论时一头扎进 `assets.bin`。
