# 挖 #11：图里的「配置ID」到底指向什么，能不能在存档里找到

**任务**：每个模块图都用 `货币配置ID` / `道具配置ID`（桥的 contract **参数类型 20** = config-id）。
今天这些是**调用方随手传的整数**，没人知道它指向的模板是否存在。这份是只读挖掘。

---

## 一句话结论

**不能。今天没有任何一个离线产物能回答「配置ID X 是否存在」。**

- **文档层**给的是**编码规格**（一个十进制 ID 的 22~28 位是"业务类型号"，并给出一张
  「类型号 → 十进制可修改范围」白名单），**不是实例登记表**——官方章节自己写明只给"读取侧与校验侧"。
- **存档层没有货币/道具的登记表**：`profile .gip` 是纯项目/关卡登记表（1185 B 全解，只有 6 个字段号）；
  `level .gil` 里唯一**按配置ID 索引**的表是 **field 15**，它今天在全部 18 个关卡里
  **一条 `资源货币`(类型 10) 和一条 `普通道具`(类型 8) 都没有**，只有一条 `背包模板`(类型 11)。
- **编辑器目录 / node-contracts** 是**节点定义**与 **UI 资产**的清单，**不是"已创建的道具/货币"清单**。
- 因此，对 demo 实际写进去的那几个 caller-supplied 整数，**能证明的只有"它们不在任何关卡的 field 15 里"**，
  不能证明"它们不存在于编辑器项目数据库的别的角落"。**field 15 是不是穷尽登记表，未证。**

**唯一能定论的实验**（§5）：手工在编辑器 UI 建**一个**货币模板 → 原生 `save` → **前后字节差分那一关的 `.gil`**。
差分出现的新字段/新条目就是货币登记表；没有，则说明登记表不在本地存档里。

### 1.4 一个必须先拆掉的陷阱：两张表的类型号**重叠**

`2.ID类型表` 其实有**两张**子表，共用同一段类型号：

- **「配置ID」表**（29 行）：类型 `1 = 单位状态 = 1077936128~1082130431`、`2 = 客户端节点图`、`8 = 普通道具…`、`10 = 资源货币`…
- **「实体ID」表**（4 行）：类型 `1 = 物件(含元件) = 1077936128~1082130431`、`2 = 造物`、`5 = 关卡`…

**类型 1、2 在两张表里名字不同、范围相同。** 所以**光凭 22~28 位的类型号无法区分一个 ID 是"配置ID"还是"实体ID"**，
必须结合它出现的**字段上下文**。本次存档挖掘正好撞上这一条（§2.6）。

**另**：`level .gil` 里的关卡 id 是 `0x40000001..0x40000012`（`(>>22)&0x7F == 0`，落在文档的
「0 = 无效」带 `1073741824~1077936127`），而文档说「关卡」是**实体ID 类型 5** `1094713344~1098907647`。
**⇒ 关卡 id / 图 id 用的命名空间**（0x40……，类型带 0）**与文档的「实体ID 关卡」带并不一致**。
文档那张表**不能**用来判定关卡/图 id 的归属。

## 2. 存档层：有没有一张可读的配置ID表？

### 2.1 存档只有两个文件种类

`tools/beyond-save/gil_container.py:1-34` 记的容器（本次实测一致）：


（原始代码或现场命令片段未随公共研究笔记分发；可用工具见目录。）


真实路径（`100000001` = 目录名 = field 39 creator uid）：

- `…/BeyondLocal/100000001/Beyond_Local_Save_Player.gip` — **1185 B**
- `…/BeyondLocal/100000001/Beyond_Local_Save_Level/*.gil` — 18 个关卡（+ `UpgradeBackup/` 里 1 份 835 副本）

> 全程**只读**：`Path.read_bytes()`，无一字节写入 LocalLow。

### 2.2 `profile .gip`：只有"项目登记表"，**没有**配置表（1185 B 全解）

`gil_container.parse_profile`（`gil_container.py:363`）只认三个字段号（`_first(fields,N)` / `_all`）：

- field 2 ×18 — 关卡引用 `{1: id, 2: name, 3: timestamp, 5: flag}`
- field 1 ×1 — 页签容器（`1 > 2 > 4[]`，`parse_tabs` 在 `gil_container.py:390`）
- field 3 ×1 — trailing（= 最后一个关卡 id）

**把 1185 B 整个递归展开**（`parse_fields` 全树），顶层字段直方图**只有** `{(1,2):1, (2,2):18, (3,0):1}`。
里面全是 page-tab 名（`root` / `未分类页签` / `自定义页签_1…`）与关卡 id `0x40000001..0x40000012`。

**⇒ `profile` 里没有任何货币/道具/背包/商店的字段，一个字节都没有。**

### 2.3 `level .gil`：**field 15 是唯一按配置ID 索引的对象表**

一个关卡 payload 有 42~45 个顶层字段（field 1..53 稀疏）。逐字段扫中文字符串后，
**唯一**带资源配置的是 **field 15**（以 demo 关卡 `1073741842.gil` 为例，field 15 = 8336 B，含 4 个 field-1 条目）：


（原始代码或现场命令片段未随公共研究笔记分发；可用工具见目录。）


**field 15 = 每个关卡一份「系统对象表」，键是配置ID**：每条 = `{配置ID, 类型标签/名称, 载荷}`。
唯一按配置ID 索引的地方，就是它。

全 18 个关卡的 field 15 一览（本次扫描，19 份文件 = 18 关 + `UpgradeBackup/` 1 份 835 副本）：

| 关卡 | field 15 | 条目 |
|---|---|---|
| 1073741825 / 829 / 831 / 832 / 833 / 834 / 835 / 838 / 839 | n=2 | 道具背包 `1119879169` · 环境 `1186988033` |
| 1073741828 / 830 / **840** / **841** / **842** | n=4 | 上面两条 + 职业 `1090519041` · `1094713345` |
| 1073741826 / 827 / 836 / 837 | **无 field 15** | （占位/空关卡） |

**⇒ 全部 18 个关卡里，field 15 里没有一条 `资源货币`(10)，也没有一条 `普通道具`(8)；
唯一的资源类是 `背包模板`(11)。** 中文字符串扫描也印证：全 18 关只出现 `背包模板`（+ demo 关的图内打印串 `货币发生变化`），
**从不出现任何货币/道具/商店模板名**。

### 2.4 全量递归扫描：**没有任何 type 8 / type 10 的字段值**

对全部 `.gil` 递归遍历 protobuf（`parse_fields`，深度 ≤9），把所有 **varint 字段值**按类型带分类。
**唯一**出现在配置带里的、被 varint 字段承载的值是：

| 类型 | 值 | 出现位置 |
|---|---|---|
| 4 职业 | `1090519041` | field 15 条目 |
| 11 道具背包 | `1119879169` | field 15 条目 |
| 27 环境 | `1186988033` | field 15 条目 |
| 1（单位状态 **或** 物件） | `1077936129..1077936135` | entity 蓝图 —— **实为 entityId**（见 §2.6） |
| 2 客户端节点图 | `1082130433..` | 仅 `1073741840.gil` |
| **8 普通道具 / 10 资源货币** | **（空）** | **全部文件，0 命中** |

**⇒ 存档里根本没有"货币模板"或"道具模板"被创建过。** demo 写进图的 `货币配置ID` / `道具配置ID`
**在这台机器的任何关卡里都对不上任何一条记录** —— 这就是"悬空引用"的字节级证据。

### 2.5 **警告**：字节窗口扫描会大量骗人

如果不去解析 protobuf、而直接在 payload 上滑 4 字节窗口找"落在 `0x40000000~0x49800000` 的整数"，
会命中几百个（本次试过：一个文件几百个"疑似货币/道具 ID"）。原因是 **IEEE-754 浮点**：`float 2.0 = 0x40000000 = 1073741824`，
`1e9 附近的 float` bit-pattern 全部落进这些带里。**所以"在存档里搜到一个像配置ID 的数字"不算证据**，
必须走 §2.4 的**结构化 varint** 路径。这条写下来，免得下一轮又踩。

### 2.6 观察：实体ID 与配置ID **在同一个带里混着**

递归扫描里 type 1 的值 `1077936129..1077936135` 看着像"单位状态配置ID"，其实是 **entityId**：
`docs/gameplan/REAL-MACHINE-RUNBOOK.md:192` 记 demo 落盘载荷含 `entityId 1077936129`。
文档的「配置ID 表 type 1 = 单位状态」与「实体ID 表 type 1 = 物件(含元件)」**范围同为 `1077936128~1082130431`**——
**同带不同物**。任何"按类型带判定它是不是一个货币配置ID"的自动化，都必须同时看它落在哪个字段。

同样，关卡 id 与图 id 都落在 `0x40……` 的 **type 0 带**（文档名"无效"）。

## 4. 判决：今天能不能判定一个配置ID 是否存在？

**分两半，说清楚：**

### ✅ 能做的（离线、只读、可复现）

1. **解码归属**：`(id>>22)&0x7F` → 该 ID 声称的业务类型；比对类型表的范围 → 是否"格式合法"。
2. **在该关卡的 field 15 里查**：如果这个 ID 是**该关卡**登记的系统对象，它就会出现在 field 15 条目里。
   **本例**：demo 关 `1073741842.gil` 的 field 15 只有 `{1119879169,1186988033,1090519041,1094713345}` —— 
   **不含任何货币(10)/道具(8) ID**。所以 demo 写的那些整数，**在本关卡的登记表里找不到。**

### ❌ 不能做的（今天的边界）

3. **不能权威地回答"配置ID X 存在吗"**，因为：
   - **field 15 是不是穷尽登记表，未证。** 它今天恰好列了 `背包模板/环境配置/自定义职业/…`，
     看着像"资源系统模板表"，但**没有任何证据说它会收录用户后来手工建的货币/道具**——
     它也可能只列"关卡默认对象"。
   - **没有任何工件记录货币/道具模板的字段名、序列化结构或所在字段**（`M2M3-currency-item.md:165` 同结论）。
   - **不存在货币/道具模板的读写入口**（桥的 op 面（见 tools/gameplan/tests/test_doctrine.py）/ CLI / MCP 全 0 命中）——连"读一个模板"都做不到。
4. **不能**凭"字段里搜到一个像配置ID 的数"下结论（§2.5 浮点假阳性）。

### 所以对 demo 的准确措辞是

> demo 图里的 `货币配置ID` / `道具配置ID` 是 caller 传的整数；**在拥有该关卡的存档里，
> 这个整数不在任何字段被登记**（§2.3/§2.4 字节证据），**因此它指向的模板在这台机器上不存在**。
> 但"存在性"的权威判定需要一个**尚未做过的实验**（§5）来锁定登记表。

## 5. 唯一能定论的实验（真机，一次就够）

**目标**：证明"货币模板登记表在不在本地存档里、是哪个字段"，从而把 §2.3 的 field 15 从"候选"升格为"登记表"。

**步骤**（全部在真机、人工操作编辑器 UI，不经过桥）：

1. 选一个**已被 field 15 覆盖**的关卡（如 `1073741842`），先 `save`，**备份**该 `.gil` 的字节 + sha256。
2. 在编辑器里 **系统菜单 →【货币与背包】→ 货币页签 →「新建」**，只建**一个**货币模板（记下它显示出的配置ID）。
   再做一次：**道具页签 → 新建一个道具模板**（记下配置ID）。**不要**做任何其它改动。
3. 原生 `save`（`scene_cli.py … save`，需当次关卡 id + `--review`）。
4. **字节差分**该关卡的 `.gil`（前后两份）：
   - 若 field 15 **多出两条条目**，且其中 `字段1` 的值 **等于第 2 步记下的配置ID**
     （类型带应为 10 / 8）⇒ **field 15 就是登记表**，此后"某配置ID 是否存在"= 读该关卡 field 15。
   - 若 field 15 **没变**，但某个**原本为空/为新出现的字段**变大了 ⇒ 货币/道具登记表在**那个字段**，
     记下它，本表的 field 15 只覆盖"系统默认对象"。
   - 若**整个 .gil 都没变** ⇒ 模板不在本地关卡存档里（在编辑器项目库/服务端），
     那就要去编辑器自己的项目存储找，而不是 `.gil`。

**成本**：一次 UAC / 一次手工建模板 / 一次 save + 两次只读读回。
**收益**：一次性把"配置ID 存在性"从"不可判定"变成"可离线判定"（若落在 field 15）或"明确不在本地"（若不在）。

**可先做的廉价前置**（纯离线）：用户"反复换存档"（工程记忆 `level-ids-are-per-save-never-pinned`）——
**去用户其它存档/其它 uid 目录里跑 §2.3 的 field 15 扫描**；只要某一关有手工建过的货币，
field 15 里就会出现 type-10 条目，一次就把登记表证实（或证伪）。
