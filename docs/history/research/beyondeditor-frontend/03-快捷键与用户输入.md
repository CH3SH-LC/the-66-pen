# 03 · 快捷键与用户输入

> **调查的问题：** 编辑器定义了哪些快捷键与用户输入绑定？它们能否映射到代码？
> **结论一句话：** 快捷键配置解出 **62 个 `BEYOND_EDITOR_SHORTCUT_KEY_*` 记号**，
> 分成 **26 个动作名** + **36 个键帽名**；动作侧覆盖节点图编辑的**画布/节点/连线/文件夹/复制**五类，
> 全部是**节点图画布语义**，**没有一条是场景编辑或资源操作的快捷键**（可信度：高，静态全量解析）
> **最后更新：** 2026-09-22

数据版：`db/raw/shortcuts.json` → 表 `shortcut`（62 行）。
查询：`SELECT action_key FROM shortcut WHERE json_extract(keys,'$') IS NOT NULL;`

> 每个键帽在树里出现**两次**：一次带单字符标记前缀（如 `!BEYOND_EDITOR_SHORTCUT_KEY_TOOL_A`），
> 一次不带（`BEYOND_EDITOR_SHORTCUT_KEY_TOOL_A`）。

### 3.1 关于那个「标记前缀字节」——**未解**

观察到 16 种不同前缀：`!` `"` `#` `$` `%` `&` `*` `+` `/` `0` `1` `5` `9` `;` `<` `=` 。

**本轮的判断：不解，并如实标注。**
- 它是 `s_alt` 字段的**首字节**（解析时被剥掉），形态像 0x21–0x3D 区间的 ASCII 字符。
- 它**不是修饰键位图**——同一位图值会重复出现在不同键上，且修饰键本身（Ctrl/Shift）也有标记。
- 合理的猜测是 protobuf 定长字段被误读（首字节恰好构成合法 tag），但**这是猜测，不是证据**。
- **因此 `shortcut` 表的 `modifier_marker` 与 `marker_decoded` 两列留空**，
  不填任何推测值——宁可空缺，不可编造。

## 六、代码落点

对 62 个 `SHORTCUT_KEY_*` 记号在 `annotated/`（12,375 个 `.cs`）里反查字面量：

| 记号类型 | 有代码落点 |
|---|---|
| 动作名（26 条） | **0 条** |
| 键帽名（36 条） | 3 条：`BEYOND_EDITOR_WPF_SHORTCUT_KEY_TITLE`、`..._TOOL_Ctrl`、`..._TOOL_Delete` |
| **合计** | **3 / 62（4.8%）** |

**怎么读这个数：**

- 动作名 0 落点**不等于这些快捷键没有实现**。快捷键配置是**数据**，
  编辑器在运行期按动作名去查文本、再按配置分发按键——动作名不必以字面量形式出现在代码里。
- 真正说明问题的是**键帽名**：只有 `Ctrl` / `Delete` / 标题 3 个被代码直接取用，
  其余 33 个键帽名的显示文本走的是**数据驱动**路径。
- **这是一条方法学提醒**：在本项目里，「grep 不到」**从来不能**证明「不存在」。

对照：`02-界面功能面/01-界面文本总表.md` §4 里，
`BEYOND_EDITOR_*` 一级桶 59 条中同样只有 **3 条**有代码落点（5.1%），
与本节独立算出的 3/62 一致——**两个独立口径互证**。
