## 调研范围与假设

**用户指令（2026-09-22）：** 深度调研千星编辑器的前端，找全前端能实现的功能及相关代码，
写在数据库内。编辑器来源：`C:\Games\Genshin Impact Game\BeyondAssets\BeyondAssistEditor`。

**本次调研的「前端」定义（假设）：**
`BeyondAssistEditor` 目录下那个**独立的 WPF(.NET) 桌面程序**——即 `BeyondEditor.exe` +
`BeyondEditor.dll` + `Resource/` 资源包。它是编辑器面向用户的界面层与业务层。

### 方法论上的一个重要差异（必须如实标注）

标准深度调研的多来源交叉验证，在**本地二进制逆向**场景下没有对应物：

## 结论摘要

**① 这个前端是什么。** 一个**自包含发布的独立 WPF(.NET) 桌面程序**：17.5 MB 混淆主程序集 +
231 MB 加密资源包（解出后是 6,453 个纯 PNG 图标）+ 242 个 .NET 运行时文件。
引用 59 个程序集，**唯一外部宿主依赖是 miHoYo 内部的 `miTools.*`**；
**不引用任何 Unity / 游戏程序集**。带单实例 Mutex、自带 `0Harmony` 运行时补丁库。
→ `01-前端架构与程序集.md`（可信度：高，静态）

**② 一个反直觉的结构发现：发布版里没有 XAML。** 程序集内 `g.resources` / `.baml` 原始字节
**0 命中**，全程序集只有 **1 个** `Window` 子类、`UserControl`/`Control`/`FrameworkElement` 子类**各 0 个**。
界面由**代码构造**。「XAML 加载失败后回退」是推断，未获运行期证实。
**实用含义：「找 XAML 读界面结构」这条路不存在文件。**
→ `06-WPF代码可实现功能面.md`（可信度：静态事实确认；回退机制为推断）

> ⚠️ **2026-09-22 更新（下一轮 `../beyondeditor-user-operations/` 更正）：上面这条只有前半句成立。**
> **XAML 确实存在** —— 从已解密的字符串表与反编译注释里找到 **48 个 `.xaml` pack URI**
> （`BeyondEditor` 28 个 + 自研控件库 `BydeCustomControl` 19 个 + 1），
> 组织成 `Xaml/Template/Explorer/...`、`Xaml/Template/InstructionGraph/...` 这样的树。
> 准确的表述是：**XAML 存在，但它的编译产物（BAML + `g.resources`）被混淆器加密**，
> 所以**磁盘字节里读不到**。
> **「原始字节搜不到」≠「这个东西不存在」** —— 这是本项目第四次犯同一个错。
> 更正后的结论反而更有用：**界面的目录结构与每个面板/对话框的名字完全可恢复**。
> 详见 `../beyondeditor-user-operations/01-方法论-界面怎么重建.md` §一。

**③ 代码的 75% 是「被提升成类型的方法引用」。** 12,300 个非重复类型里，
**9,218 个是 delegate 类型**——混淆器把方法引用做成了独立类型。
真正承载业务的是 **2,941 个 class**，界面层 **136 个**。
→ `06-WPF代码可实现功能面.md`（可信度：高，静态全量）

**④ 功能清单本体：80 条功能，19 个功能域。** 节点图 20、场景编辑 14、资源 5、编辑工具 5、
通信 4、数据 4、环境 4、界面 4、调试 4、玩法 3、特效 3、性能 2、存档 2，等等。
其中 **15 条可达（`reachable=yes`）**、5 条已证不可达、60 条未验证。
→ `db/features.json` / 表 `feature`（可信度：逐条带证据）

**⑤ 命令层全集：44 条操作名。** 全部落在 20 个混淆类型上，
其中 **9 条集中在两个命令宿主**（`kg9jHSKBgsfObR2IXdPf` 30 成员、`NQ6Rasu5Wb3lL511Sp4j` 72 成员）。
按对象类别的动作矩阵显示：实体支持「改名/删除/聚焦/阵营/标签/挂图/删组件」，
**但没有「创建」和「移动/缩放」**——操作名词表里根本没有这两个动词。
→ `04-操作名与命令绑定.md`（可信度：高，静态全量枚举）

**⑥ 通信只有一条真实业务通路：** 编辑器作 **TCP 客户端**发给对端的 **1018 公共命令通道**
（响应 1019，帧带 `0x0656/0x0666` 魔数 + XOR `0xEA`），承载 **13 个通道标识**与 **≥23 条命令**。
**编辑器本地只登记 3 个 `wpf*Service`**——7 个 `beyond*Service` 的处理器**在对端进程**。
派发**永不抛错、客户端不做校验、回执不是确认**。
→ `05-前后端通信通道.md`（可信度：通道身份实测；命令语义基本未验证）

**⑦ 蓝图的树结构是自证的：** 13 个顶层分类（`【超限】`6 + `【经典】`6 + 1 个操控运动器）
× 2–5 个二级功能组 × 10–127 个叶 = **465 条目录名**。
「查询节点 / 运算节点」是通用底座；**「事件节点」只有服务端蓝图有**。
→ `02-界面功能面/03-菜单与面板结构.md`（可信度：高，键名直接给出结构）

**⑧ 能放什么，有一份具体名单：** **2,424 个元件图标**（建造/结构/道具/岩石/植被/光），
**410 个工具栏按钮**，**2,973 个特效标记**（角色技能/怪物技能/动物行为/元素反应）。
但**「能放」这件事本身仍未接通**——图标存在 ≠ 放置接口可用。
→ `02-界面功能面/02-图标与视觉资源.md`（可信度：高，清单与磁盘 100% 对齐）

**⑨ 能力边界：读得通，写得窄。** 读：可遍历资源注册表、读模型字段、观察入站帧。
写：只有**改名 / 删除**这一小片有实机留证。
**创建、几何变换、原生保存三类都是「未找到可调用入口」（`not_found`），不是「已证伪」。**
已证伪的 11 条（D1–D11）逐条列在 `07-能力边界与缺口.md` §二。
→ `07-能力边界与缺口.md`（可信度：高，逐条有实验留证）
