# 05 · 消息编号路由 —— 1018 入站全链与全跳表

> **调查的问题：** 一个 1018 帧从游戏侧入口走到命令分发表，中间经过什么？
> 24 个注册消息编号各自落到哪？服务名是怎么被比对的？
> **结论一句话：** 包分发器 `0xa223420` 读 `[envelope+0x18]` 的 ushort 走
> **`0xa223ba8` 的 24 项相对跳表**，其中**只有 8 项是真处理器**（其余 16 项共用一句 `ret` 尾声）；
> 1018 经 `0xa223810` → `0xa223e00` → `0x918dd40`（**il2cpp `Dictionary<string,Entry>.TryGetValue`
> + 接口虚调用**）到达命令分发表，然后回发 **1019**（`mov dx,0x3fb`）。
> **服务名的比较发生在 il2cpp 字典内部，链上没有任何字符串比较指令。**
> **可信度：静态（全表字节直读 + 有界反汇编）。** 最后更新：2026-09-22

## 一、包分发器 `0xa223420` 与 24 项跳表

| 项 | 值 |
|---|---|
| 分发器 | `0xa223420`（读 `[envelope+0x18]` 的 ushort） |
| 跳表位置 | **`0xa223ba8`**，24 × int32，值 = **目标 − 表首地址**（rel32） |
| 编号范围 | 表内 1001–1024；表外另有 **1025**（`0x401`）与 **3001**（`0xbb9`）走单独比较路径 |
| 真处理器 | **8 项** |
| 共用 no-op 尾声 | **16 项** → `0xa223993`（`add rsp,0x28; pop rdi; pop rsi; ret`） |

| 编号 | 目标 | 说明 |
|---:|---|---|
| 1001 | `0xa22347c` | 编辑器首帧 / 握手 |
| 1002–1009 | `0xa223993` | **不处理**（共用尾声） |
| 1010 | `0xa223665` | 处理器（用途未证） |
| 1011 | `0xa2236b4` | 处理器（用途未证） |
| 1012 | `0xa223993` | 不处理 |
| 1013 | `0xa223703` | 处理器（用途未证） |
| 1014 | `0xa223752` | 处理器（原生同步载荷） |
| 1015 | `0xa223993` | **不处理** —— 与前端侧「工厂已注册但从未观测到」一致 |
| 1016 | `0xa2237c4` | 处理器（性能/内存上报） |
| 1017 | `0xa223993` | **不处理** —— 但前端侧实测到 20 次入站 ⇒ **另有接收者** |
| **1018** | **`0xa223810`** | **命令通道** |
| 1019–1023 | `0xa223993` | 不处理（1019 是**出站**响应，本来就不该在入站表里） |
| 1024 | `0xa22383b` | 处理器（要求同步接口） |
| 1025 (`0x401`) | `0xa22361a` | 表外，经 `0xa223453 cmp eax,0x400; ja 0xa2235ba` |
| 3001 (`0xbb9`) | `0xa2235cf` | 表外 |

> **「表里写的是不处理」≠「没有接收者」。**
> `1017`（前端实测入站 **20** 次）与 `1020`（入站 **5** 次）在这一层都是 no-op，
> 说明它们**另有接收者**（见 `06-出站方向-游戏发给编辑器.md`）。
> 反之 `0`（空控制包，入站 **975** 次）**根本不在这个表里**。

`0x918dd40` 的形态是：

**链上没有任何字符串比较指令。** 比较发生在 il2cpp 字典内部
（`0x166f5370` FindEntry / `0x166f5850` / `0x166f6240`）。

**服务名存在哪：** 不在 exe 里。它们是 **il2cpp 字符串字面量**，
只有 `mov ecx, <metadata 索引>; call 0x4f4440` 这样的**运行时初始化守护桩**；
字面量本体在 **`global-metadata.dat`**，而该文件头是 **mhy 加密**
（首 dword = `0x59484D` = `'MHY'`，不是标准 IL2CPP 的 `0xFAB11BAF`，整体熵 **7.996**），**字符串堆不可读**。

**四种编码的实测结果**（`probe-bytes.py` 单遍 mmap）：

| 载体 | FNV1a-le | ASCII | UTF-16LE | UTF-8 |
|---|---|---|---|---|
| `YuanShen.exe` | 0 | 0 | 0 | 0 |
| `global-metadata.dat` | 0 | — | 0 | 0 |

**对照组证明方法有效**：命令名 `FocusEditObj` 在 exe 里**只有 FNV1a 命中**、明文 0 命中。
另穷举 **14 种哈希函数 × 8 个服务名 = 224 次全映像扫描**（djb2 / sdbm / crc32 /
xxHash32 / Murmur3 / Mono `GetHashCode` / fnv1 / fnv1a-utf16 …）—— **全 0 命中**。

🔴 **一条必须记在账上的方法论结论：**
`global-metadata.dat` 是加密的 —— 连 `GameObject` / `Service` 这种**必然存在**的词
在里面也是 0 命中。**因此在这个文件上的任何「0 命中」都不能用来证明「不存在」**，
只能得出「这个编码下读不出来」。这也是服务名判为 **`undecidable`（存在但加密）**
而不是 `not_found` 的原因。**「读不到」和「找不到」是两件事。**

⇒ 准确说法是：**存在，但在加密元数据里**（`undecidable`）。
完整机制（三个函数、7 个注册点、虚 `GetHashCode`）见 `04-服务路由层.md`。

## 四、分发函数与 `0x918dd40` 之间隔着什么

两个命令分发表**各有 0 个 E8 直接调用者**（全映像扫描）。

> **本轮独立复核**（不依赖既有工具）：用 numpy 在 `.text` + `il2cpp` 全段上扫
> **每一条 `E8`（call rel32）与 `E9`（jmp rel32）**，把 `指令地址 + 5 + rel32`
> 折算回 RVA 后与目标比对 ——
> `0x914de40`：**0 处**；`0x768d170`：**0 处**。

`probe-bytes.py --u32` 对这两个 RVA 全映像**各只命中 1 次**，
且都在 `.upx0` 的「每方法 `{begin,end,metadata_ptr}` 登记表」（`0x195917c0` / `0x194b6214`）
—— 那不是 vtable，只证明方法存在。

**可达性来自一次运行时接口虚调用：** `0x918de72 call rsi`，
`rsi` 取自字典值对象的**接口槽**（内联接口偏移扫描 `0x918ddf1..0x918de58`，
或 helper `0x4ea8e0`）。签名吻合：
`0x918dd40` 传 `(cmdNameString, list1, list2, 0)`，
`0x914de40` 序言 `r14=this / rbx=rdx / r12=r8 / rsi=r9`，随后对 rdx 的 System.String 做 FNV-1a。

⇒ **`0x914de40` / `0x768d170` 只是「高置信推断的目标」，不是「静态可证的绑定」。**

## 五、一处必须记下来的悬案：1018 字段顺序

观测到的是：

| 层 | 字段位置 |
|---|---|
| envelope | payload@`+0x10`，id@`+0x18` |
| payload | 命令名@`+0x18`，**服务名@`+0x20`**（服务名才是字典键） |

这与前端侧记录的 wire tuple 次序「(请求号, 服务名, 命令名, 参数表)」**相反**。
纯静态**无法定论**谁是谁 —— 记 `undecidable`，不选边。
下一轮若取得逐帧读回的入站 1018（前端侧当时也缺这一条），这条自然解决。
