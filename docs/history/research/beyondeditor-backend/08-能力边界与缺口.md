# 08 · 能力边界与缺口

> **调查的问题：** 这份「前端接口 → 后端实现」的对应关系**能支持什么**、**不能支持什么**？
> **结论一句话：** 它能回答「**这条命令在游戏侧有没有实现、实现在哪个函数里、那个函数读了什么参数**」
> —— 在**候选名 / 编码 / 扫描段 / 已检查分发形式**四个边界之内。它**不能**回答「这条命令现在能不能被安全调用」，
> 因为本轮**全部结论都是 `static`**：没有执行过任何游戏代码、没有读过游戏进程内存、没有发过报文。
> **可信度：本节是对本轮结论适用范围的自我限定。** 最后更新：2026-09-22

---

## 一、这份对应关系**能**回答什么

| 问题 | 能答 | 依据 |
|---|---|---|
| 这条前端命令在游戏侧有没有实现？ | ✅ | 全映像 4 对齐哈希穷举（`01-`） |
| 实现在哪个函数？比较点在哪？处理分支在哪？ | ✅ | `0x914de40` / `0x768d170` 完整解码（`02-` `03-`） |
| 这个处理器读几个参数、什么类型？ | ✅ | 统一参数访问器家族 + 判别值映射（`02-` §二） |
| 它调用了哪些下游函数？ | ✅ | 有界反汇编一层展开 |
| 哪些命令共享同一段实现？ | ✅ | 逐条比对（Tag 共用 `0x914dbc0`、Faction 共用 `0x914c900`…） |
| 后端接受的命令集与前端暴露的命令集谁大？ | ❌ **已推翻** | 初版说后端多 2 条；后续一轮证明那 2 条前端**都有入口**（命令名被写成了 XOR 折叠常量）。**未发现真正的差集** |
| 1018 帧走到哪、怎么回 | ✅ | `05-` |
| 「只有两处分发」这句话有没有统计支撑？ | ❌ **计数论证已作废** | 初版期望多算 4 倍；现在只剩「聚簇与断层」的形态判据，且限于四个边界内（`01-` §六） |

## 二、这份对应关系**不能**回答什么

| 问题 | 为什么不能 |
|---|---|
| 这条命令现在能不能被安全调用？ | 本轮**从未执行**任何游戏地址；「代码长这样」≠「运行期这样走」 |
| 参数的实际**取值**范围与业务语义 | 只读到「读第几个参数、什么类型」，读不到字段名与取值域 |
| 处理器的**效果**是什么（改名成功？删除生效？） | `static` 只能到「调用了哪个函数」 |
| 全局钩子 `0x768d80e` 会不会拦截 | 置位条件未知（`03-` §四）⇒ **表里有 ≠ 运行时走表** |
| 服务名到分发表的选择在运行时是否真按推断走 | 那一跳是**接口虚调用**，静态无表可证（`05-` §四） |
| 另外 3+ 个服务通道的分发器在哪 | 服务表有 7 个注册点，本轮只对上 2 个 |
| `global-metadata.dat` 里的类名 / 方法名 / 服务名 | 该文件 **mhy 加密**，字符串堆不可读 |

## 三、三种「没有」，必须分开写

本轮所有否定性结论都严格落在下面三类里，**不许混为一谈**：

| 状态 | 含义 | 本轮的实例 |
|---|---|---|
| **`disproved`** | 有**正面反证**证明它不成立 | 本轮**一条也没有**。所有「后端不处理」的结论都只是「查不到」 |
| **`not_found`** | 查不到，但**没有证据**说它不存在 | 6 条无落点命令、3 个未定位的服务分发器、`call rsi` 的目标、若干下游语义 |
| **`undecidable`** | 现有方法**判不了** | 服务名（存在但加密）、1018 字段顺序、哈希扫描方法的固有盲区 |

> 本项目历史上三次严重错误都源自**用字符串检索的缺失去证明不存在**。
> 因此本轮的措辞一律是
> 「**在这张映像的这个编码下没有**」，而不是「后端没有」。
> 例外只有一处可以写强一点：**6 条无落点命令**，因为除了哈希（4 种对齐）
> 还查了 ASCII / UTF-16LE / UTF-8 三种明文、并对两张分发表做了完整逐条比对
> —— 但仍然只能说「**没接住**」，不能说「游戏没有这个能力」。

## 四、本轮踩到的两个自伤（写下来给下一轮）

| # | 错误 | 后果 | 教训 |
|---|---|---|---|
| 1 | **只扫 4 字节对齐**的立即数 | 命中 90 处、`.text` 里 0 处，几乎全漏 | x64 的 imm32 **不保证对齐**；`DoImport` 的常量落在偏移 ≡2 (mod 4) |
| 2 | 给函数表 `end` **写死上界 `0x10000000`** | 1,145,693 条 `.pdata` 记录里**丢掉 587,428 条（51%）**，正好是 il2cpp 段上半部分 | **sanitize 用的常量必须来自被分析对象本身**（段表算出的映像上界是 `0x1a343800`），不能凭印象写一个「够大」的数 |

两条都是**子智能体在实际追踪下游调用目标时撞出来的**，
说明「把工具交给多个独立读者使用」本身就是一种有效的交叉验证。

## 五、与上一轮前端侧能力边界的关系

上一轮 `../beyondeditor-frontend/07-能力边界与缺口.md` 的结论是
「**读得通，写得窄**」：读能遍历资源、读模型字段；写只有**改名/删除**有实机留证，
创建 / 几何变换 / 原生保存三类是 `not_found`。

本轮把那个结论的**后端一侧补齐了**：

| 前端侧当时的说法 | 后端侧本轮的对应 |
|---|---|
| 「创建」没有前端触发 | 后端 25 条主表里**确实没有 `Create*` 动词** —— 只有 Add/Apply/Delete/Modify/Focus/Request |
| 「几何变换」没有前端触发 | 后端 25 条里**确实没有位置/旋转/缩放命令** |
| 「原生保存」没有 1018 命令名 | 后端 7 条导入导出表里**确实没有 Save** |
| 「7 个 `beyond*Service` 处理器在对端进程」 | ✅ 2 张表覆盖其中 2 个服务；另 3 个服务的分发器**本轮未定位** |
| ~~「PCG 服务命令仅字符串、无派发调用点」~~ | ❌ **前端侧错了**：三条 PCG 命令都有完整 1018 派发点（`Oe5aspiVGooyp47o5s0q.cs:12596/12601/12606`，本轮独立复核）。**前端侧漏了** |
| ~~「`create`/`delete`/`modifyname` 属 `beyondAudioService`」~~ | ❌ **归属写错了**：它们属 `beyondInstructionGraphService` |

**结论改成更准确的说法：**
前三行是两侧独立证据链互相吻合，是本轮**最强的交叉验证形式**
（前一节靠**前端代码**说「没有创建」，本轮靠**游戏映像穷举**说「后端也没有创建命令」）。
但最后两行提醒：**前端侧的枚举是不可靠的** —— 它既漏（PCG 有派发点被写成没有），
也错（服务归属写错）。**「前端没写」不能推出「不存在」**，
这条在本轮被正面证伪了一次。
