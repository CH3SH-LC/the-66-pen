## 调研范围与假设

**用户指令（2026-09-22）：** 「从前端接口进一步调查，从而定位前端接口对应的后端功能，进行全量调查。

**上一轮的位置：** 上一轮（`../beyondeditor-frontend/`）把**前端**即 `BeyondAssistEditor`

**本轮的对象：「后端」= 游戏进程内、接住这些接口的那一侧。**
具体落点：`C:\Games\Genshin Impact Game\YuanShen.exe`

## 结论摘要

**① 最关键的一步：找到了前端接口名到后端地址的那把钥匙。**
游戏侧**不比较字符串**，它比较的是命令名的 **FNV-1a 32 位哈希**。
用 5 组已知真值验证 **5/5 精确命中**（`DoImport=0xc9824659`、`DoExport=0xd8aae5e2`、
`FocusEditObj=0x78eb3304`、`AddInstructionGraphForPrefab=0x1a33f6f9`、
`ApplyPrefabInstanceChange=0x68677bd6`）。
→ 这一条一旦成立，「前端有哪些命令被后端接住」就变成一个可以在整张映像上
**穷举**的问题，而不是抽样问题。见 `01-`。

**② 前端 36 条业务命令里，30 条在游戏侧有确切落点。**
而且**全部 30 条只落在两个函数里**：
- **`0x914de40`**（4,775 B，**完整解码**）：25 条命令 —— 实体/预制体的聚焦、改名、
  标签、阵营、组件删除、节点图挂载、复制体。结构是一棵按哈希比较的**判定链**
  （`cmp ecx, <hash>` + `ja`），每条命令一个处理分支，未命中一律落到 `0x914f084`。
- **`0x768d170`**（1,803 B，**完整解码**）：7 条命令 —— DoImport / DoExport /
  ImportDebugLog / ImportAllDebugLog / ImportPerformanceReport / DeleteDebugLog /
  RefreshExistDebugLogReport。
见 `02-` 与 `03-`。

**②b ~~后端比前端多 2 条命令 ⇒ 后端是超集~~ —— 这条已被后续一轮推翻。**
初版说两张表里有 2 个命令名（`AddInstructionGraphForPrefab`、`ApplyPrefabInstanceChange`）
不在前端那 44 条操作名里，因此后端是超集。
🔴 **后续的「用户操作」调研（`../beyondeditor-user-operations/`）证明这两条前端都有入口**：
`ApplyPrefabInstanceChange` 由场景对象右键的「**应用**」发出，
`AddInstructionGraphForPrefab` 由资源条目拖放发出。
之所以没被列进操作名清单，是因为**前端把命令名写成了 XOR 折叠常量**而不是字面量。
⇒ **本轮没有发现后端与前端真正的命令差集**；
「按字面量枚举前端命令名」才是当初得出「超集」的原因。

**③ 「只有两个」是一个**有限范围内**的结论，不是「后端能力已穷尽」。**
在 345,055,744 字节的可执行段上做 **4 种字节对齐**的单遍扫描
（x64 指令里的 imm32 不保证 4 字节对齐，只扫对齐位置会漏掉绝大多数真比较 ——
`DoImport` 的常量就落在 4 字节偏移 ≡2 处），匹配 2090 个候选名的哈希：
- 命中 774 处；
- 落到 593 个函数；
- **其中成串出现「命令形状」名字的，只有 `0x914de40`(25) 与 `0x768d170`(7)**，第三名只有 4；
- ⚠️ **计数论证已作废（独立质量审查后修正）**：初版把「4 种字节对齐」误当成
  「4 × N 个位置」，随机期望**多算 4 倍**（应为 **≈168**，不是 672）。
  修正后残差 693 **远高于**期望 —— 于是**两个方向都用不了**：
  均匀随机模型不成立（短名过散布），既不能说「残差是噪声」，也不能说「残差里还有表」。
  详见 `01-` §六。**现在站得住的判据是「聚簇与断层」，不是计数**；
- 数据段（`.rdata`/`.data`/`_RDATA`/`.tls`/`.upx0`）里候选哈希**共 6 处**，
  在这个范围里**未发现**表驱动分发表（⚠️ 只查了字面出现，**没有查间接索引结构**）；
- 长命令名（≥12 字符）在映像里出现 1–3 次；
  短通用名（`name`153 / `value`100 / `offset`52 / `index`44 …）散落在几十个函数里，
  是 il2cpp 字段名哈希留下的过散布（**推断**），与命令分发形态不同。
见 `01-` §五–§六。

**④ 6 条命令在游戏侧没有落点，但要分成两类，不能一锅端。**

| 命令 | 服务 | 判定 | 依据 |
|---|---|---|---|
| `EndLoadAllDebugLog` | 编辑器本地（入站） | **`disproved`** | 它**根本不是下行命令**：字面量在 12,375 个反编译类型里只出现在 `PSQ99ZKPMVVhBlIP6pR2.zll1ASKPPG90rdIZ1Ymn.cs` 的**入站命令名比较**（line 85 → 调自己的本地方法 line 87，定义 line 200）；该类在 `producer.cs:144` 被注册进**编辑器本地服务表**。**「上行/下行」配对的是 `ImportAllDebugLog`（有 FNV 分支）与它（没有）** |
| `PlayMusic` / `PlaySoundEffect` | `beyondAudioService` | `undecidable` | **下行事实已确证**（`EF8cLvuBwl2IuhblDnsW.JVFa9yuBBE11Zhdy7ce5.cs:224` / `:165` 构造 1018，10 个参数）；**但「游戏侧有没有处理器」判不了** |
| `ModifyPCGInstanceName` / `DeletePCGInstance` / `FocusPCGInstance` | `beyondPCGInstanceService` | `undecidable` | 同上，**下行派发点确有**（`Oe5aspiVGooyp47o5s0q.cs:12596/12601/12606`，本轮已独立复核） |

**判不了的理由不是「懒得查」，是机制性的**：服务名查找走**托管对象虚 `GetHashCode`**
（`0x166f5370` 里 `mov rax,[key]; call qword ptr [rax+0xe0]`），
**命令名走托管字典的路静态根本看不见**。
所以这 5 条只能得到**有界负面结论**：「在编译期常量哈希 switch 里没有分支」，
不能升级为「游戏不处理」。

🔴 **本轮推翻了上一轮前端侧的一条结论**（见「变更记录」）：
前端文档写 `beyondPCGInstanceService` 的命令「**仅字符串，无派发调用点**」——**这是错的**，
三条 PCG 命令都有完整的 1018 派发点。前端侧当时漏了。

**⑤ 服务名在游戏映像里 0 命中 —— 但这不是「找不到」，是「读不到」。**
`beyondEditObjService` 等 7 个 `beyond*Service` 名字的四种编码在 `YuanShen.exe` 里**全 0 命中**；
另穷举 **14 种哈希函数 × 8 个服务名 = 224 次全映像扫描**，也**全 0 命中**
（对照组证明方法有效：命令名 `FocusEditObj` 只有 FNV1a 命中、明文 0 命中）。
真正的原因是**服务名根本不参与静态哈希比较**：
键是托管对象，哈希由 il2cpp 内部的**虚 `GetHashCode`** 完成
（`0x166f5370` 里 `mov rax,[key]; call qword ptr [rax+0xe0]`）。
名字本体在 **`global-metadata.dat`**，而该文件是 **mhy 加密**的
（首 dword `0x59484D` = `'MHY'`，整体熵 **7.996**）——**连 `GameObject` 这种必然存在的词都是 0 命中**。

🔴 **方法论后果**：**在这个文件上的任何「0 命中」都不能用来证明「不存在」。**
服务名的状态因此是 **`undecidable`（存在但加密）**，不是 `not_found`。
机制全貌（三个函数 `0x918dd40`/`0x918dbd0`/`0x918da10`、7 个注册点、接口三槽）见 `04-`。

**⑥ 1018 全链钉死，24 项跳表全解。** 包分发器 `0xa223420` 读 `[envelope+0x18]` 的 ushort
走 `0xa223ba8` 的 **24 项相对跳表**，其中**只有 8 项是真处理器**，其余 16 项共用一句 `ret`。
1018 = 表内索引 17 → `0xa223810`（精确类型检查）→ `0xa223e00`（1,296 B）→
`0x918dd40` 服务查找 → 命令分发表；随后 `mov dx,0x3fb` **回发 1019**。
**「表里写不处理」≠「没有接收者」**：1017（前端实测入站 20 次）与 1020（5 次）在这层都是 no-op。
见 `05-`。

**⑦ 出站方向（游戏 → 编辑器）：**出站**只有一个原语** ——
`0xddef670(连接对象, 消息号, 载荷)`，下游 `0xe937280`（限速+时戳）→ `0x80bbba0`（真实写帧）；
连接对象恒为 `[0x555fac8+0xfbf0]`（22 个调用者的 RIP 相对地址**全部解析到同一全局**）。
6 类实测入站帧里 **5 类**的发送者已定位（`1019` `1020` `1017` `1011` `3006`），
第 6 类（编号 `0`，观测 **975 次最多**）**没有发送点**，
但量化为**严格 1 Hz**（租约秒数 == 入站次数，120→120 / 25→25 / 3→3，25 个 run 无例外）。
⚠️ **多个发送者用尾 `jmp` 而非 `call`，E8-only 扫描会漏**（`1011` 就是这样漏掉的）。
见 `06-`。

**⑧ 分发函数没有静态调用者。** `0x914de40` 与 `0x768d170` 在全映像**各有 0 个 E8 直接调用者**，
也**各有 0 个 RIP 相对引用**；可达性来自 `0x918dd40` 里的一次**运行时接口虚调用**（`0x918de72 call rsi`）。
⇒ 「表在哪」是静态确定的，「谁在运行时调它」是**推断**。见 `05-` §四。

**⑨ 两处「静态路径 ≠ 运行期路径」的硬证据。**
- `0x768d170` 里的前置全局钩子 `0x768d80e`：标志位置位时**整个命令分发被委托给 `0xd4af450`，绕过哈希表**。
- 服务层每个入口也带**字节标志 + 指针表**覆盖开关（`0x54c710a/b/c`、
  `[[0x555fac8]+0x224b0]+0xad9e0/9f0/9f8/ada00`）。
两处的标志与指针**全在 BSS（磁盘上是 0）** ⇒ **「表里有」不等于「运行时走表」**。
见 `03-` §四与 `04-` §五。
