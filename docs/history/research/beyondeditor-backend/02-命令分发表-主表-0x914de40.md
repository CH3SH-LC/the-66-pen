# 02 · 命令分发表主表 `0x914de40` —— 25 条命令的后端实现

> **调查的问题：** 落到 `0x914de40` 这 25 条命令，后端各自做了什么？
> **结论一句话：** 25 条命令挤在**一个 4,775 字节、完整解码**的函数里，用
> `cmp ecx, <FNV1a>` 判定链分发；命中后落到 25 个处理分支。它们**不是一套通用实现**，
> 而是**共享调度骨架 + 若干组复用**：改名/标签/阵营/删除各有共用下游，
> 7 条 Focus\* 里有 3 条**逐字节同构**、2 条共用同一下游、1 条是双模式转发。
> **可信度：静态（有界反汇编，逐条复核）。** 最后更新：2026-09-22

---

## 一、分发表本身

| 项 | 值 |
|---|---|
| 函数起点 / 终点 | `0x914de40` / `0x914f0e7` |
| 大小 | **4,775 字节**（capstone **完整解码**，`complete=true`） |
| 比较条数 | **33**（覆盖 25 个不同命令名；少数命令在链上出现两次） |
| 未匹配回退 | `0x914f084`（各条 `jne` 的公共目标） |
| 序言 | `mov rsi,r9 / mov r12,r8 / mov rbx,rdx / mov r14,rcx` ⇒ 4 个实参 |
| 哈希循环 | `0x914e0a1` 起：`mov ecx,0x811c9dc5` + 逐字符 `xor` + `imul 0x1000193`（见 `01-`） |
| 静态调用者 | **0 个 E8 直接调用者** —— 经 `0x918dd40` 的运行时接口虚调用到达（见 `05-`） |

**判定链的读法（一个必须澄清的坑）：** 链的形状是「**二分下降 + 相等则落地**」。
一条 `cmp ecx, <hash>` 后面的条件跳转有两种含义：

| 跳转形态 | 含义 | 不是 |
|---|---|---|
| `ja <本表另一条 cmp>` | 二分搜索的**子树入口** | 处理分支 |
| `jne 0x914f084` | 不相等 → 回退 | 处理分支 |
| `je <链外地址>` | 相等 → **处理分支** | — |
| `jne 0x914f084` **且顺序落地** | 相等会顺序落地 → **处理分支就是下一句** | — |

**只记「跳转目标」会把 3 类中的 2 类当成处理分支。** 本项目的
`raw/dispatch-tables.json` 里因此同时存了 `branch_target`、`fallthrough_rva`、
`handler_entry`、`handler_source` 四个字段；`handler_entry` 是机械推断，
**下表的值是逐条有界反汇编复核过的**。
25 条里有 4 条（FocusEditObj / FocusLight / FocusScreenshot / FocusBeyondTileMap）
的原始 `branch_target` 曾是回退地址 `0x914f084`，已被纠正。

### 3.4 聚焦类（9 条）—— 「共享骨架 + 两套实现」

**先给结论：不存在单一的「聚焦实现」函数。** 7 条 Focus\* 分成两条路：


（原始代码或现场命令片段未随公共研究笔记分发；可用工具见目录。）


| 命令 | 哈希 | 分派 | 处理器 | 参数 | 做什么 |
|---|---|---|---|---|---|
| `FocusEditObj` | `0x78eb3304` | `0x914e8a5` | `0x914f5f0` | (int id) | A 路；取不到就静默返回 |
| `FocusPrefabInstance` | `0xb202598a` | `0x914ec20` | `0x914f0f0` | (int id) | A 路，**只差查哪张表** |
| `FocusLight` | `0xe703f83d` | `0x914e91c` | `0x914f7b0` | (int id, int mode) | **双模式转发**：mode==0 原样复用 A 路；mode==1 → `0xcb5f330(id)` 后**直接 `call 0x914f0f0`**（即 FocusPrefabInstance 的处理器）；其他 → 骨架 |
| `FocusEsp` | `0x9ffa4fa9` | `0x914ef4d` | `0x914c680` | (int id) | B 路，面板常量 (3,3) |

| `FocusScreenshot` | `0xc7280e4f` | `0x914e639` | `0x914d560` | **(float × 6)** | **参数形状独一无二**：6 个 float 重组成两个 Vector3；先 `0x914cb10(this,1)` 切面板，再骨架 (1,-1) |
| `FocusCharacter` | `0x3f5d30b2` | `0x914eb29` | `0x914c630` | (int id) —— **不读它** | 79 B 纯切面板：`mov ecx,3; xor edx,edx; xor r8d,r8d; jmp 0x6f408c0`。**传入的 id 被丢弃** |
| `FocusBeyondTileMap` | `0x7ca8b102` | `0x914e247` | `0x914d450` | (int id) | B 路里唯一**先自行解析对象**（`0x721cac0`）再切面板 (0,-1) |

**三条硬证据支撑「不是一套通用实现」：**

1. **逐字节同构的三份实例**：`FocusEsp` / `FocusLocalBullet` / `FocusDropGather`
   分别是 215 / 222 / 222 字节，结构完全相同，差异只有三个静态槽与面板常量。
   同构 ≠ 共用 —— 是**同一个模板复制了三份**。
2. **直接 call 另一条命令的处理器**：`FocusLight` 的 mode==1 支路直接
   `call 0x914f0f0`（FocusPrefabInstance 的处理器）。这是**复用**的硬证据。
3. **参数形状不统一**：7 条是单个 int，`FocusLight` 多一个 int，
   `FocusScreenshot` 是 6 个 float。**「Focus 都收一个 int」是错的。**

**共用的基建**（静态观察）：面板调度骨架 `0x6f408c0`（**只被这 7 条 Focus 系使用**，
有界扫描确认）、只切面板的 `0x914cb10`、服务定位器 `0x1389bfc0`、
全局会话静态 `0x555fac8`、委托调用桩 `0x5160`、闭包类 `0x557a388`（6 条 Focus 共用）。

> `FocusCharacter` 的处理器**丢弃参数** ⇒ 它的聚焦目标 **not_found**，
> 不能写成「已聚焦角色」。
