# 04 · 服务路由层 —— 服务名怎么选中分发表

> **调查的问题：** 一个 1018 请求只带命令名，不带「用哪张表」。那么服务名是怎么选中分发表的？
> 服务名存在哪？
> **结论一句话：** 机制是 **`Dictionary<string, ServiceEntry>.TryGetValue(服务名)` + 接口虚调用**；
> 服务名是**托管字符串对象**，其哈希由 il2cpp 内部的**虚 `GetHashCode`** 完成 ——
> **它不参与任何静态哈希比较**，所以「换一种哈希函数就找到了」这条路**已被 224 次扫描排除**。
> 服务名的**正文只在加密的 `global-metadata.dat` 里**，磁盘上读不到。
> **可信度：机制为静态（有界反汇编）；服务名状态为 `undecidable`（存在但加密）。** 最后更新：2026-09-22

---

## 一、三个函数：查 / 注册 / 注销

| 函数 | 大小 | 入参 | 做什么 |
|---|---:|---|---|
| `0x918dd40` | 445 B | `(M, key, a3, a4, a5)` | `[M+0x18]!=0 → 返回 0`；`0x166f5370`（= `Dictionary.FindEntry`）查 key；命中后解析 value 的**接口槽 0** 并调用 `(value, a3, a4, a5, 0)` |
| `0x918dbd0` | 368 B | `(M, key, value)` | 先对 value 调**接口槽 1**（注册回调，rdx=0），再 `0x166f5850`（= `Insert`）写入字典 |
| `0x918da10` | 433 B | `(M, key)` | 查表 → **接口槽 2** 回调 → `0x166f6240`（= `Remove`） |
| `0x918d790` | — | — | `Clear`，同样走槽 2 |

三者共享同一个**接口类型静态槽 `0x55d4298`**（BSS）；槽号 0/1/2 由
`methods[接口 offset + slot]` 决定，慢路径走 `0x4ea8e0`。

**接口三个槽的语义（推断，但形态吻合）：**

| 槽 | 语义 |
|---:|---|
| 0 | **Invoke**（分发一条命令） |
| 1 | 初始化 / 注册回调 |
| 2 | 释放 / 注销 |

## 二、注册：`0xa224da0` 的 7 个服务

`0xa224da0` 在 `mode == 1` 分支建 7 个服务对象并注册。**7 次注册已 1:1 对齐**
（键槽 ↔ 类槽 ↔ getter）：

| # | 键静态槽 | 类静态槽 | 备注 |
|---:|---|---|---|
| 1 | `0x57de218` | `0x5605d20` | |
| 2 | `0x57de230` | `0x5605d28` | |
| 3 | `0x57de1f0` | `0x5605d30` | |
| 4 | `0x57de200` | `0x5605d38` | |
| 5 | `0x57de160` | `0x5605d40` | 额外调 `0xb6a4a10` |
| 6 | `0x57de1c8` | `0x5605d48` | 内部再 new 一个对象 B 填字段 |
| 7 | `0x57de150` | `0x5605d50` | **尾跳**注册，故 E8 只有 6 条 |

7 个类槽是**连续 8 字节槽** ⇒ 元数据里相邻的 7 个类型。
另有 7 个 54 字节的**孪生 getter**（`0x11c72c60` / `0x11c73690` / `0x11c73b00` /
`0x11c74980` / `0x11c74a00` / `0x11c74a40` / `0x11c76d00`）token 完全对应，
形态是「返回自己的名字」。

> 与上一轮前端侧的观察对上：前端有 **7 个 `beyond*Service`** 通道标识。
> 数量吻合，但**本轮没有把第 i 个注册点绑定到第 i 个服务名** —— 见 §五。

## 三、服务名到底在哪 —— 磁盘上没有

### 3.1 两种编码 × 两个载体，全 0 命中

| 载体 | FNV1a-le | ASCII | UTF-16LE | UTF-8 |
|---|---|---|---|---|
| `YuanShen.exe` | 0 | 0 | 0 | 0 |
| `global-metadata.dat` | 0 | — | 0 | 0 |

**对照组证明方法有效：** 命令名 `FocusEditObj` 在 exe 里**只有 FNV1a 命中**（`0x914e116`），
明文 0 命中 —— 说明「0 命中」不是扫描器坏了。

### 3.2 换哈希函数也不行（224 次扫描全 0）

穷举 **14 种哈希函数 × 8 个服务名 = 224 次全映像扫描**，**全 0 命中**：
djb2 / djb2x / sdbm / java31 / crc32 / adler32 / xxHash32 / Murmur3 /
Mono `String.GetHashCode` / fnv1 / fnv1a(utf16) / 小写 fnv1a / …

### 3.3 为什么 —— 服务名根本不参与静态哈希比较

**关键机制**：键是**托管对象**，不是字符串常量。哈希由 il2cpp 内部的**虚 `GetHashCode`**
完成 —— `0x166f5370` 里是 `mov rax, [key]; call qword ptr [rax+0xe0]`。

⇒ 「服务名用另一个哈希函数」这个猜想**不成立**：它压根不在静态比较里。

### 3.4 那它在哪

**在加密的 `global-metadata.dat` 里。**

| 证据 | 值 |
|---|---|
| 首字节 | `MHY\0`（不是标准 IL2CPP 的 `0xFAB11BAF`） |
| 整体熵 | **7.996** |
| `GameObject` / `Service` 这类**必然存在**的词 | **0 命中** |
| `ctable.dat` / `startup-metadata.dat` / `StreamingAssets` | 全 0 命中 |
| `svc_catalog` | 是着色器变体目录，**排除** |
| beyond 相关插件 / 托管 DLL | **不存在** |

⇒ **这条必须记在账上：在 `global-metadata.dat` 上的任何「0 命中」都不能用来证明「不存在」。**
这也是本轮把服务名判为 **`undecidable` 而不是 `not_found`** 的原因 ——
**存在，但读不到**。「读不到」和「找不到」是两件事。

运行期形态：服务名物化成 `Il2CppString` 存进静态槽
`0x57de150 / 0x57de160 / 0x57de1c8 / 0x57de1f0 / 0x57de200 / 0x57de218 / 0x57de230`；
**全映像找不到任何写这些槽的引用，只有读** —— 写发生在别处（metadata 初始化 / AOT 桩）。

## 四、两套哈希，不要混

| 对象 | 算法 | 在哪 |
|---|---|---|
| **命令名** | **FNV-1a 32，逐 UTF-16 码元** | `0x914de40` / `0x768d170` 内联：`mov ecx,0x811c9dc5` + `movzx word ptr[…]` + `imul ecx,esi,0x1000193`，再 `cmp ecx,<常量>`（33 / 8 个比较点） |
| **服务名** | **不参与静态哈希比较** | 键是托管对象，哈希由 `0x166f5370` 里的**虚 `GetHashCode`** 完成 |

## 五、服务 ↔ 分发表的映射：只到语义层，**没到地址绑定**

| 服务 | 命令数 | 落在 `0x914de40` | 落在 `0x768d170` |
|---|---:|---:|---:|
| `beyondEditObjService` | 15 | **15** | 0 |
| `beyondExportService` | 7 | 0 | **7** |
| `beyondInstructionGraphService` / `beyondEffectService` / `beyondAudioService` | 6 | 0 | 0 |

**硬证据只有形态匹配：**
- 两表**零个 E8 调用者**、**零个 RIP 相对引用**（`find-native-callers.py` + `find-pe-riprefs.py`）；
- 两表入参 `(this, string, obj, obj)` 与 `0x918dd40` 调接口槽 0 的实参形态一致；
- 两侧命令集**互斥吻合**（15/15 vs 0/15；7/7 vs 0/7）。

⇒ 「`beyondEditObjService` → `0x914de40`、`beyondExportService` → `0x768d170`」**成立**，
但**记为 `inferred`，不是实测**：**「注册点 → 哪张表」无法离线证明** ——
类身份由 `Il2CppClass*` 决定，而类槽 `0x5605d20..0x5605d50` 在磁盘上是 **BSS**（全零）。

> **另一个必须记的坑：服务层自己也有运行期覆盖开关。**
> 每个入口都带**字节标志**（`0x54c710a/b/c` 等）与**指针表**
> （`[[0x555fac8]+0x224b0]+0xad9e0/9f0/9f8/ada00`，对应实现 `0xd37ac70` / `0xd1bca50` /
> `0xd4ec940` / `0xd184180`）。标志与指针**全在 BSS（磁盘为 0）**
> ⇒ **哪份实现真正生效只能在运行时判定**。这也是「服务名在哪处理」可能另有答案的原因。
>
> 与 `0x768d170` 里那个全局钩子 `0x768d80e`（`03-` §四）是**同一种设计模式**：
> **磁盘上的静态路径不一定是运行期走的那条。** 本轮两处都撞到了它。
